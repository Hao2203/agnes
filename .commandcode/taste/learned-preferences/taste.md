# Learned Preferences
- Organizes Rust projects as a cargo workspace with crates in subdirectories (e.g. `agnes/core`, `agnes/llm-openai`, `agnes/agent`, `agnes/cli`), sharing `workspace.package` and `workspace.dependencies`. Confidence: 0.9
- Prefers hexagonal layering: write the pure, I/O-free core first, then assemble upper layers (ports, transports, driver, adapters, CLI). I/O code — HTTP transport, port traits, tool registries — must not live in the core crate; the core stays pure computation. Confidence: 0.95
- Requires I/O to be async, not blocking: use `#[async_trait]` dyn-compatible port traits, tokio for fs/process, and established HTTP libraries (e.g. reqwest) rather than hand-rolled or synchronous clients; achieve runtime swappability by swapping adapter/transport crates, not by keeping ports synchronous. Confidence: 0.9
- Prefers explicit state-machine (type-state) design for agent/protocol logic: each state is its own type, transitions consume state and return effects interpreted by an upper driver layer, making illegal sequences non-compilable. Confidence: 0.8
- For LLM integration, wants provider adapters behind a common port trait — OpenAI-compatible format first, extensible to other APIs later. Confidence: 0.7
- Uses `jiff` as the time library in Rust projects (not chrono/time). Confidence: 0.9
- For brand-new projects, expects real initialization via cargo (root workspace `Cargo.toml`, `.gitignore`, all member crates present before building), not just scattered source files. Confidence: 0.8
- Communicates in Chinese; respond in Chinese. Confidence: 0.7
- Expects CLI programs to be robust for Chinese/IME terminal input: multi-byte UTF-8 editing and backspace must never crash or silently exit the session (read lines as bytes and decode lossily), invalid input degrades instead of aborting, and the CLI always shows feedback — silent blocking with no prompt is treated as a bug. Confidence: 0.75
- Wants interactive agent/chat CLIs to carry full session memory across inputs: each line continues the accumulated transcript (seed history threaded through the core agent config, full history returned with each run result and fed into the next request), with an explicit reset command (`/new`) to start fresh — not one isolated task per input. Confidence: 0.8
- When a program accumulates several pieces of related state (system prompt, conversation history, tool calls/results), wants them consolidated into one dedicated domain struct that owns and manages the context (e.g. a `Context` type with methods to build the per-run transcript and to reset) — instead of scattering loose fields (`system`, `history: Vec<Message>`) across config structs and CLI code, and instead of the host manually assembling message arrays. Confidence: 0.85
- For fallible Rust collection constructors, wants both entry points rather than one: an iterator-based one (`from_iter`, accepting `IntoIterator`) for genuine iterator sources, plus a buffer-taking one (`from_vec(Vec<T>)`) for callers that already hold a `Vec` — the latter moving the existing buffer straight into the shared allocation (`Arc::from`) instead of making callers re-`collect` it. When a `Vec` already exists, it should be moved, not re-collected; `from_iter` should delegate to `from_vec`. Confidence: 0.85
- Allocation-conscious Rust design: cares about avoiding unnecessary allocations and element copies in hot/constructor paths, will add API surface specifically to eliminate an extra intermediate allocation even at the cost of a second method, and will revisit an implementation to shave a remaining allocation when std already offers a cheaper path. Confidence: 0.85
- Avoids unnecessary conversion layers in constructor signatures: prefers dedicated conversions (`TryFrom<&str>`, `TryFrom<String>`) over a `new(impl Into<String>)`-style generic argument, which just introduces a meaningless extra conversion. Confidence: 0.8
- Places core domain types physically in the core crate, not in a shared utility crate: a type carrying domain meaning (e.g. `Content`, a non-empty user/model text) belongs in the core module (`core/src/content.rs`, `agnes_core::content::Content`) even if generic/reusable, reserving the utility crate for dependency-free, domain-agnostic building blocks (e.g. `NonEmpty<T>`). Confidence: 0.85
- Strongly prefers making illegal states unrepresentable through types: enums should carry their required data directly in each variant (so variants like a "tool-use" stop reason can't exist without calls, eliminating runtime validation errors such as `EmptyToolUse`) rather than a variant plus a separate emptiness check; and invariant-bearing values get dedicated newtypes — a non-empty collection type (e.g. `NonEmpty<T>`, cheaply clonable, `AsRef<[T]>`, guaranteed at least one element) and a non-empty-content type (e.g. `Content`) — often placed in a small shared utility crate. Confidence: 0.9
- Names modules/types/crates after domain concepts, not implementation patterns or niche architectural jargon: rejects evocative-but-opaque names — e.g. `machine` (replaced by `turn`, since the module is turn-driven with `ModelTurn`/`ToolsTurn`) and `agnes-ports` (hexagonal-architecture jargon whose meaning is unclear without knowing that theory, replaced by `agnes-io`) — in favor of plain, self-explanatory names that match what the code does and fit the project's single-word crate style (`core`/`util`/`agent`/`cli`), so names stay self-consistent with their contents. Confidence: 0.8
- Prefers one-to-one correspondences to be structural, not conventional: instead of two parallel collections (`calls: NonEmpty<ToolCall>` + `outputs: Vec<ToolOutput>`) relying on a length check at construction, wants them zipped into a non-empty tuple array (`NonEmpty<(ToolCall, ToolOutput)>`) so the pairing is bound at construction and can never be mismatched or separated later. Confidence: 0.75
- Wants domain data structures subdivided by shape rather than modeled as one struct with optional fields: message/transcript entry types (e.g. `AssistantMessage`) should be enums whose variants distinguish the mutually-exclusive cases (e.g. `Text(Content)` for pure text vs `ToolCalls { content: Option<Content>, calls: NonEmpty<ToolCall> }`), so states like "content and tool_calls both absent/empty" are non-constructible. Confidence: 0.8
- Public interfaces must not leak a crate's internal string types: in `agnes/core/src`, internal string wrappers (e.g. the `cold-string`/`ArcColdString` type) must not appear in public signatures; when a public API needs a string, expose a standard-library string type instead, keeping the internal representation an implementation detail. Applies regardless of which internal string type is chosen (`Arc<str>` or `ArcColdString`) — the public face uses `&str`/`String` and domain newtypes only. Restated explicitly by the user as part of the string storage policy. Confidence: 0.9
- For read-heavy strings that definitely cannot be inlined and are never modified, prefers `Arc<str>` (std) over a third-party string wrapper, and cares that the constructor let an already-owned string move into that allocation (e.g. `impl Into<Arc<str>>`) rather than forcing a re-copy. Strings that might be inlineable belong to `ArcColdString` instead — see the string storage policy entry above. Confidence: 0.85
- Uses the `url` crate's `Url` for URLs rather than hand-rolled string handling: a URL boundary type should be a thin validated newtype delegating to `Url` (e.g. `BaseUrl(Arc<Url>)` that parses once in `FromStr`, checks the `http`/`https` scheme, normalizes the path to exactly one trailing slash, and builds endpoints via `Url::join`) — not bespoke prefix sniffing plus `format!` concatenation, while still keeping the parse-once boundary type instead of dropping it. Confidence: 0.75
- When a value is not mutated but needs to be `Clone`d/shared, wraps it in `Arc` so clones are refcount bumps rather than deep copies. Confidence: 0.8
- String storage policy, explicitly stated by the user (correcting an earlier "全部用 `Arc<str>`" misconception): strings that definitely cannot be short-string-inlined and are never mutated (e.g. tool output content, tool descriptions) use std `Arc<str>`; strings that could benefit from inlining (model names, system prompts, tool names, tool-call ids/parameters, `Content`) use the `cold-string` crate's `ArcColdString`. This supersedes the earlier "reversed cold-string entirely, dropped the dependency" stance — `cold-string` is a permanent part of the policy for the possibly-inlineable case, not a dependency to eliminate. Confidence: 0.9
- Prefers reusing a well-known library's existing types over hand-rolling equivalents: when an established crate already expresses the concept (e.g. the `http` crate's `Request`/`Response`/`Method`/`StatusCode`), use those types directly instead of defining bespoke `HttpRequest`/`HttpResponse`/`HttpMethod` — fewer conversion layers and native interop with other libraries that use the same types (reqwest). Confidence: 0.85
- Error types must not carry `String` payloads: error enums should hold typed underlying errors (e.g. `std::io::Error`, `anyhow::Error`) as variants — typically via `#[from]`/transparent `thiserror` enums — preserving the full error source chain rather than flattening failures into a formatted string. Confidence: 0.9
- Works plan-first: poses design questions and expects a written plan (with architecture analysis and open questions) before any code changes, then green-lights implementation with a terse directive (e.g. a single word like "执行"/"go"). Prefers reviewing the approach up front rather than the agent coding immediately. Confidence: 0.6
- Enforces strict layer boundaries along the dependency direction: a lower-level component (the pure core state machine) emits the semantic model input and lets the upper driver layer assemble the concrete request, attaching only what the core has no business knowing (the model name). The core owns the semantic prompt — which includes both the conversation history and the tool definitions offered this round — but not the model; lower layers must not hold or know data they don't use, so configuration the state machine can't use (e.g. the model name) belongs as a parameter supplied by the host, not a field in its config. Confidence: 0.85
- Wants the model-input type broken into semantically named fields rather than a bare container: a `Prompt` should expose `input` (the model input history) and `tools` (the tool definitions offered this round) as distinct, domain-named fields, not a generic `messages: Vec<Message>` list. Confidence: 0.75
- Avoids speculative/premature fields (YAGNI): data structures should carry only what is actually consumed — adds fields when a real consumer needs them rather than pre-declaring placeholders; e.g. dropped `base_instructions` and left out generation params like `tool_choice` until they are wired. Confidence: 0.6
- Prefers a single representation of the system prompt over duplicating it: keeps the system prompt as the first message of the conversation history (the transcript/wire path already turns it into a leading `system` message) instead of extracting a separate `base_instructions` field alongside it. Confidence: 0.65
- Secrets (API keys, credentials and similar sensitive values) must be carried by the `secrecy` crate's types instead of a bare `String`/`Arc<str>`-style plain string — e.g. an `ApiKey` type should wrap `secrecy`'s secret type so exposure is explicit and values can't leak via `Debug`. Confidence: 0.85
- Expects Rust changes verified workspace-wide before being called done: `cargo fmt --all`, `cargo clippy --workspace --all-targets -- -D warnings` (warnings are errors), and `cargo test --workspace`, plus a grep/`cargo tree` check that a removed dependency left no traces. Confidence: 0.55
- Wants the session/context object to be the single source of truth that also records an ordered log of all runtime events (not just messages): each step appends its events into the context so the full run can be replayed/persisted/telemetried, while the events returned to the host are only for immediate reporting. Confidence: 0.7
- Wants environment/capability information for the run (e.g. the tools available this turn) to live inside the session context object rather than as loose fields in the agent config. Confidence: 0.7
- Explicitly defining the agent core as a sans-io, event-loop-driven state machine: the core never performs I/O — each step is presented to the core as an input (e.g. `ToolStarted`/`ToolFinished` fed back by the driver) and the core replies with an effect the outer driver executes (e.g. a `RunTool` action; the driver's only job is IO). The run taxonomy for this project is fixed: `step` = one model round trip; `turn` = one complete agent run composed of multiple steps (the "task" concept is dropped entirely); a turn ends only at the final reply, an interruption, or exhaustion of the step budget. Confidence: 0.7
- Wants request construction (context → model request) to be a pluggable, host-supplied converter whose implementation alone decides how to build the prompt and request, with the core offering only a standard/default projection — request-building strategy is not hard-coded in core. Reaffirmed by name as a host `RequestBuilder`. Confidence: 0.8
- Wants conversation messages modeled as just one kind of event in the same single ordered event log (e.g. `Event::Message(Message)` alongside the turn/lifecycle variants), with the message list exposed only as a projection/filter over that log — so the total order of everything that happened is always reconstructible from one stream, instead of messages living in a separate list that can drift out of order relative to the events around them. Confidence: 0.85
- Uses `jj` (Jujutsu) for version control on this repo (`.jj` present alongside `.git`), explicitly self-identifying as a jj user. Expects history investigations to account for jj semantics: rewritten/hidden commits kept alive by `refs/jj/keep/*` (visible to `git log --all` but not to plain `jj log`), and prefers read-only jj commands (`jj log`/`show`/`bookmark list`/`op log`) over anything that mutates the working copy. Confidence: 0.85
- Interrogates design decisions before accepting them: asks targeted "why" questions about specific API/signature choices (e.g. "why does `update` return `Events`"), and expects the answer to not just justify the choice but lay out the reasoning — the cost of the design, the alternatives considered, and why they were rejected. Confidence: 0.55
- For sans-io state machines, wants pending effects held as a true FIFO queue (`VecDeque`) with a `poll_actions() -> Option<Action>` API that hands out exactly one action per call — rather than a `Vec` drained wholesale via a `drain_actions() -> Vec<Action>`. Stated as a correction ("actions 使用队列，poll_actions 方法每次拿一个") applied across core, driver and adapter tests. Confidence: 0.75
